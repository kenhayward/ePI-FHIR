# docs/

Supporting documentation and materials that are not the primary specifications.

## Contents
- `exports/` - generated Word (.docx) exports of the specs/design Markdown, for review and
  distribution. Generated by `tools/export-docx.sh`; git-ignored by default (regenerate on demand).
- `source-material/` - input and reference material. Git-ignored by default (may be large or
  licensed; keep local).

The canonical, version-controlled documents are the Markdown files under `specs/` and `design/`.

## Document retention

Regulated-domain work has to be able to show what a document said at a given point in time. The
policy is:

- **The Markdown under `specs/` and `design/` is the record.** It is version-controlled, so any
  historical state is recoverable from git, and every change arrives through a reviewed pull
  request with an audit trail.
- **Generated `.docx` exports are derivatives, not records.** They are reproducible from the
  Markdown at any commit via `tools/export-docx.sh`, so committing them on every change would
  add binary churn without adding information.
- **Issued documents are retained against a tag.** When a document is circulated for review or
  sign-off, generate the exports from a tagged commit and attach them to that tag or release.
  A signed `.docx` then maps to an exact commit, which is what an inspector needs.
- **Requirements traceability** lives in `design/traceability/`, generated from the
  specifications and checked in CI, so the requirement-to-delivery chain cannot silently drift.

If the `.docx` exports ever need to be in-tree rather than attached to tags, that is a one-line
change to `.gitignore` - a deliberate decision, not a default.
