# Capability 5 - Master Data & Identifiers (MDM)

## 5.1 Purpose & scope
Links ePI content to regulated **product master data** using ISO IDMP and EMA SPOR: it resolves and references substance, product, packaging, organisation, and referential identifiers, and maintains the **product <-> packaging <-> label association model**. The system **references** master data (system of record is SPOR and/or an internal MDM/RIM platform); it does not master it. It holds a governed local replica/cache and reacts to upstream changes.

Out of scope: authoring/owning master data; regulatory submission of product data.

## 5.2 Actors & flows
- **Author** associates a label to its product/packaging.
- **Integration process** syncs referenced master data from SPOR/MDM (via #24).
- **Administrator** manages source precedence and cache policy.

Primary flows: resolve identifiers during ingest/authoring (with #1, #2); associate a label document to product/packaging identity; subscribe to and apply upstream master-data updates; on a relevant change, emit impact events to Change Management (#8).

## 5.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-MDM-001 | Reference ISO IDMP identifiers for substance, medicinal product, packaged product, and organisation. | M |
| CAP-MDM-002 | Integrate with EMA SPOR services (SMS substance, PMS product, RMS referential, OMS organisation) and/or an internal MDM/RIM platform as the system(s) of record. | M |
| CAP-MDM-003 | Maintain the product <-> packaging <-> label association model linking each label document to the regulated product/packaging it describes. | M |
| CAP-MDM-004 | Resolve and validate identifiers used in content, flagging unresolved or ambiguous references. | M |
| CAP-MDM-005 | Hold a governed local replica/cache of referenced master data with synchronisation and version tracking. | M |
| CAP-MDM-006 | Detect upstream master-data changes to referenced entities and emit impact events to #8 (and #20). | M |
| CAP-MDM-007 | Define source-of-truth precedence when multiple sources exist (e.g. SPOR vs internal MDM). | S |
| CAP-MDM-008 | Expose an identifier resolution and association API to #1, #2, #3. | M |
| CAP-MDM-009 | Record provenance and effective dates for referenced master-data snapshots used by an approved label. | S |
| CAP-MDM-010 | Handle stale-cache and unavailability gracefully (last-known-good, staleness flags), without blocking authoring where policy allows. | S |

## 5.4 Content & data model
Referenced FHIR resources: `MedicinalProductDefinition`, `PackagedProductDefinition`, `ManufacturedItemDefinition`, `AdministrableProductDefinition`, `Ingredient`, `SubstanceDefinition`, `RegulatedAuthorization`, `Organization`; SPOR keys (SMS/PMS/RMS/OMS IDs). **Association record** links a label `Bundle`/`Composition` to product/packaging identity with effective dates. Local replica holds snapshots + version/source metadata.

## 5.5 Standards & regulatory mapping
ISO IDMP (11615/11616/11238/11239/11240); EMA SPOR service model and APIs; FHIR MedicinalProductDefinition module. Referential terms coordinate with #6 (EDQM etc.).

## 5.6 Lifecycle / owned state
Owns **local association records** and **cache freshness state** (fresh, stale, unresolved). Does not own master-data lifecycle (upstream).

## 5.7 Business rules & validation
Identifiers on an approved label must resolve to a known master-data entity; apply source precedence; a change to referenced master data raises an impact event (never silently alters an approved label); stale/unavailable master data is flagged and handled per policy.

## 5.8 Interfaces
- **Exposes:** identifier resolution + association API; master-data-change events (#20 -> #8).
- **Consumes:** SPOR/MDM/RIM via #24; #6 (referential terminology); #21 (precedence/cache config); #19 (audit).

## 5.9 Acceptance criteria / conformance
- A label associates to a valid product/packaging identity; an unresolved identifier is flagged and blocks approval per policy.
- A SPOR update to a referenced entity produces an impact event consumed by #8.
- An approved label records the master-data snapshot/version it relied on.

## 5.10 Dependencies
#24, #2, #6, #8, #20, #19, #21; foundational to #1, #3, #11, #12.

# Capability 6 - Terminology & Code System Management (TRM)

## 6.1 Purpose & scope
Manages the **code systems and value sets** the system binds to and validates against, and provides terminology services (validate, expand, lookup, translate). Covers SNOMED CT, EDQM standard terms, UCUM, MedDRA, ISO 639 (language) and 3166 (country), LOINC, and EMA/FDA controlled vocabularies, with **versioning** and license controls. Depended on by content (#2), templates (#3), mapping (#10), validation (#11), and compliance (#12).

Out of scope: authoring clinical terminologies themselves (licensed sources are imported/managed, not created).

## 6.2 Actors & flows
- **Terminology administrator** imports releases, manages value sets, bindings, and licenses.
- **Author** consumes bound value sets indirectly through guided authoring (#3).
- **Integration process** imports scheduled terminology releases (via #24).

Flows: import/maintain code systems and value sets; define bindings; expand value sets for authoring pickers; validate codes at author/validate time; manage versions and deprecations; provide cross-scheme maps to #10.

## 6.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-TRM-001 | Host and manage code systems, value sets, and concept maps (FHIR `CodeSystem`, `ValueSet`, `ConceptMap`). | M |
| CAP-TRM-002 | Provide terminology operations: validate-code, expand, lookup, and translate. | M |
| CAP-TRM-003 | Manage licensed terminologies (e.g. SNOMED CT, MedDRA) with license/access controls and usage constraints. | M |
| CAP-TRM-004 | Version code systems and value sets with effective dates and retirement/deprecation handling. | M |
| CAP-TRM-005 | Publish terminology **bindings** (element -> value set + binding strength) consumed by #2, #3, #11. | M |
| CAP-TRM-006 | Provide concept maps for cross-scheme mapping feeding regulatory mapping (#10). | S |
| CAP-TRM-007 | Import terminology releases on a schedule and track source versions (via #24). | M |
| CAP-TRM-008 | Support value-set expansion suitable for interactive authoring pickers (performance-bounded). | S |
| CAP-TRM-009 | Validate a code against its bound value set and the version effective for the content's date. | M |
| CAP-TRM-010 | Expose terminology capability via a FHIR terminology service interface. | S |

## 6.4 Content & data model
FHIR `CodeSystem`, `ValueSet`, `ConceptMap`; a **binding registry** (element/section -> value set + strength); **license metadata** per terminology; version/effective-date lineage. Config-as-data linkage with #21 for bindings and market-specific value sets.

## 6.5 Standards & regulatory mapping
FHIR terminology module; SNOMED CT; MedDRA; EDQM standard terms; UCUM; LOINC; ISO 639/3166; EMA/FDA controlled vocabularies. EU and national schemes bind different value sets to comparable elements - handled via #10 profiles referencing #6 value sets.

## 6.6 Lifecycle / owned state
Owns **terminology and value-set versions and their state** (active, deprecated, retired) and binding definitions.

## 6.7 Business rules & validation
A bound coded element must carry a code valid in the bound value set at the applicable version; binding strength (required/extensible/preferred) governs enforcement; license constraints are enforced on access/expansion; deprecated concepts are flagged; changing a binding is a versioned, audited action.

## 6.8 Interfaces
- **Exposes:** terminology operations (validate/expand/lookup/translate); binding registry; concept maps.
- **Consumes:** external terminology sources via #24; #21 (binding/config); #19 (audit).

## 6.9 Acceptance criteria / conformance
- A required-bound field rejects an out-of-value-set code and accepts a valid one.
- A value set expands within the authoring performance budget.
- Terminology versions are tracked; validation uses the version effective for the content.
- A licensed terminology is inaccessible to unlicensed users/operations.

## 6.10 Dependencies
#24, #21, #19; used by #2, #3, #10, #11, #12, #8.
