# Capability 7 - Lifecycle & Version Management (LCM)

## 7.1 Purpose & scope
The **system of record for the label content lifecycle**: a configurable state model (draft, in-review, approved, superseded, withdrawn), immutable versioning, effective dating, supersession and withdrawal, and full history reconstruction. Critically, it separates **internal lifecycle state** from **per-market regulatory-approval state** (D1 Section 6 decision).

Out of scope: approval routing UX (#16); the act of signing (#19); publication mechanics (#14).

## 7.2 Actors & flows
Author, reviewer/approver, publisher, regulatory ops. Primary flow: create draft -> in-review -> approved -> (published via #14) -> superseded or withdrawn. Supporting: version branching for variants (with #9), effective-date scheduling, reconstruction of any prior version.

## 7.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-LCM-001 | Provide a configurable lifecycle state model with explicitly allowed transitions. | M |
| CAP-LCM-002 | Version every label as immutable snapshots with a version lineage. | M |
| CAP-LCM-003 | Maintain **internal lifecycle state** separately from **per-market regulatory-approval state**. | M |
| CAP-LCM-004 | Support effective dating: when an approved version becomes effective. | M |
| CAP-LCM-005 | Support supersession (a new approved version supersedes a prior) and withdrawal. | M |
| CAP-LCM-006 | Reconstruct the full content and metadata of any historical version. | M |
| CAP-LCM-007 | Enforce transitions through workflow (#16) and permissions/segregation of duties (#17). | M |
| CAP-LCM-008 | Manage concurrent editing via locking and/or branching with defined merge/conflict rules. | S |
| CAP-LCM-009 | Link each version to the change/variation (#8) and, where relevant, submission that produced it. | M |
| CAP-LCM-010 | Emit lifecycle/state-change events (#20). | M |
| CAP-LCM-011 | Pin the content snapshot (including reusable-unit versions per policy) at approval. | M |

## 7.4 Content & data model
Version graph (nodes = immutable version snapshots; edges = supersession/branch); state attributes (internal state; per-market regulatory-approval state); effective-date fields; links to change (#8), template version (#3), master-data snapshot (#5).

## 7.5 Standards & regulatory mapping
Supports QRD/EU versioning practice and per-market approval semantics; approval signing conforms to Part 11/Annex 11 via #19. No single external standard owns the state model - it is configurable (#21).

## 7.6 Lifecycle / owned state
**Owns the label lifecycle** - the central state authority. All other capabilities read label state from here.

## 7.7 Business rules & validation
Only transitions permitted by the model are allowed; approval requires segregation of duties (author != approver); superseded/withdrawn versions are immutable and retained; a new approved version pins its content snapshot; effective-date rules govern when publication may occur (#14).

## 7.8 Interfaces
- **Exposes:** lifecycle/version API; state-change events; version reconstruction.
- **Consumes:** #16 (approval routing), #17 (permissions/SoD), #19 (audit/e-signature), #8 (change linkage), #14 (publication trigger), #2/#3/#5 (snapshot content).

## 7.9 Acceptance criteria / conformance
- An unpermitted transition is rejected; a permitted one is recorded with actor and timestamp.
- Any prior version is reconstructed faithfully.
- A market can hold a different regulatory-approval state from the internal state on the same content.
- Approval by the author of the content is blocked (SoD).

## 7.10 Dependencies
#16, #17, #19, #8, #14, #20, #2, #3, #5.

# Capability 8 - Change Management & Impact Analysis (CHG)

## 8.1 Purpose & scope
Handles **source changes** (CCDS/CDS updates, clinical safety signals) and drives their consequences: change/diff tracking across versions, **downstream impact analysis** across products/regions/affiliates/labels/sections, generation and tracking of change/variation tasks, and linkage to regulatory submissions/variations and back to the triggering signal. Also consumes master-data-driven impacts from #5.

Out of scope: authoring the changed content (#2/#3); submitting variations (RIM, via #24).

## 8.2 Actors & flows
Global regulatory, safety/PV, affiliate regulatory, reviewer. Flow: register a source change/signal -> compute impact set -> generate per-label change/variation tasks -> track propagation to each affected label version (#7) -> link submissions (#24) -> close when propagation is complete.

## 8.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-CHG-001 | Intake source changes: CCDS/CDS updates and clinical safety signals, manually and via integration (#24). | M |
| CAP-CHG-002 | Compute downstream **impact sets**: affected products, markets, affiliates, labels, and sections, using the content/reuse graph (#2) and product associations (#5). | M |
| CAP-CHG-003 | Provide change/diff tracking (redline) across label versions (#7). | M |
| CAP-CHG-004 | Generate and track change/variation tasks per affected label. | M |
| CAP-CHG-005 | Link a change to regulatory submissions/variations (#24) and to the triggering signal/source. | M |
| CAP-CHG-006 | Record **CDS-origin traceability**: associate each affected section with the source change, feeding #12's no-origin checks. | M |
| CAP-CHG-007 | Provide a propagation-completeness dashboard (which affected labels are done/outstanding). | M |
| CAP-CHG-008 | Consume master-data change impacts from #5 and fold them into impact analysis. | S |
| CAP-CHG-009 | Prevent closure while any affected label remains untracked/outstanding. | M |
| CAP-CHG-010 | Emit change lifecycle events (#20) and feed reporting (#23). | S |

## 8.4 Content & data model
Change/signal record (source, type, description, date, origin references); impact set (resolved affected entities); diff artifacts; variation/submission links; per-label task links; CDS-origin links (section -> change).

## 8.5 Standards & regulatory mapping
Interfaces with RIM/variation processes (#24); aligns to pharmacovigilance signal handling context; supports EU variation and national change processes at the linkage level.

## 8.6 Lifecycle / owned state
Owns **change/signal record states** (raised, impact-assessed, in-progress, submitted, closed). Label states remain with #7.

## 8.7 Business rules & validation
Impact analysis must be complete before a change can progress; no affected label is left untracked; CDS origin is recorded for affected sections; closure requires all propagation tasks resolved; changes to reused content units propagate to all referencing labels (via #2 reuse graph).

## 8.8 Interfaces
- **Exposes:** change/impact API; impact sets; propagation dashboards; CDS-origin links (to #12).
- **Consumes:** #2 (content/reuse graph), #5 (master-data impacts), #7 (versions/diff), #10 (market applicability), #24 (submissions), #20 (events); feeds #12, #23, #19.

## 8.9 Acceptance criteria / conformance
- A CCDS change produces a complete, reviewable impact set across all affected markets/labels.
- Each affected label is tracked through to its variation/submission; the change cannot close while any is outstanding.
- Every affected section carries a CDS-origin link consumable by #12.
- A change to a reused content unit surfaces every referencing label.

## 8.10 Dependencies
#2, #5, #7, #10, #24, #20, #23, #12, #19.

# Capability 9 - Localisation, Multi-region & Translation Management (LOC)

## 9.1 Purpose & scope
Manages **market variants** (country x language x regulator) and delivers **in-system translation management**: translation workflow, translation memory (TM), glossary/termbase, and linguistic review. Given the EU's 24+ languages, translation is first-class. External TMS integration is an optional future path (via #24), not in current scope.

Out of scope: authoring core content (#2/#3); the label lifecycle itself (#7).

## 9.2 Actors & flows
Affiliate regulatory user, translator, linguistic reviewer, global regulatory. Flow: derive a market/language variant from a core/source label -> translate section content leveraging TM/termbase -> linguistic review -> align to core when the source changes (with #8).

## 9.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-LOC-001 | Model market variants (country x language x regulator) linked to a core/source label. | M |
| CAP-LOC-002 | Provide in-system translation management: workflow, translation memory, glossary/termbase, and linguistic review. | M |
| CAP-LOC-003 | Perform structured, section-level (in-context) translation preserving the content structure (#2). | M |
| CAP-LOC-004 | Leverage content reuse (#2) and templates (#3) so shared content is translated once and reused. | S |
| CAP-LOC-005 | Track translation status per variant and per section; flag translations as **stale** when the source changes (with #8). | M |
| CAP-LOC-006 | Support at least the EU's official languages and required scripts/directionality. | M |
| CAP-LOC-007 | Enforce affiliate/market scoping (#17) and segregation of translator vs approver roles. | M |
| CAP-LOC-008 | Provide an optional integration hook for an external TMS (via #24), disabled by default. | C |
| CAP-LOC-009 | Emit localisation/translation events (#20) and feed reporting (#23). | S |

## 9.4 Content & data model
Variant model (core -> variant links, locale = BCP-47/ISO 639+3166); translation units (segment/section-level) with status; translation memory store; termbase/glossary; linguistic-review records. Locale terms bound via #6.

## 9.5 Standards & regulatory mapping
ISO 639 (language) and 3166 (country) via #6; BCP-47 locales; EU multilingual QRD expectations; market variant structure targets #10 profiles.

## 9.6 Lifecycle / owned state
Owns **translation status state** per variant/section (untranslated, translated, in-review, approved, stale). Variant label lifecycle remains with #7.

## 9.7 Business rules & validation
A source-content change marks dependent translations stale (via #8) and blocks approval until re-translated/reviewed per policy; linguistic review is required before variant approval where configured; TM is leveraged but human review governs; translator and approver must differ (SoD).

## 9.8 Interfaces
- **Exposes:** translation workflow API; TM/termbase services; variant management.
- **Consumes:** #2 (structure/reuse), #3 (templates), #6 (locale terms), #7 (variant lifecycle), #8 (staleness triggers), #16 (review/approval), #17 (scoping/SoD), #20 (events); optional #24 (external TMS).

## 9.9 Acceptance criteria / conformance
- A market/language variant is derived and translated using TM, preserving structure.
- A change to the source flags all dependent translations stale.
- Linguistic review is enforced before approval where configured.
- Variants are correctly scoped to their affiliate/market.

## 9.10 Dependencies
#2, #3, #6, #7, #8, #16, #17, #19, #20; optional #24.

# Capability 10 - Regulatory Mapping & Conformance Profiles (REG)

## 10.1 Purpose & scope
Defines **what each market's target should look like**: per-scheme **conformance profiles**, cross-scheme **mappings**, and **national extensions**. It is the source of truth that templates (#3) target and that validation (#11) and completeness (#12) check against, and it supplies transforms to migration (#4). New markets/regulators are added by configuration (#21), not code.

Out of scope: applying the checks (that is #11/#12); authoring content.

## 10.2 Actors & flows
Regulatory standards owner, template owner, administrator. Flow: define/maintain conformance profiles per scheme (EU EMRN, SPL, national) -> define cross-scheme mappings -> manage national extensions -> version and publish profiles/mappings for consumption.

## 10.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-REG-001 | Maintain conformance profiles per regulator/market (FHIR `StructureDefinition`/IG level): mandatory sections, cardinalities, terminology bindings. | M |
| CAP-REG-002 | Maintain mappings between schemes (FHIR ePI <-> SPL; EU <-> national) via `ConceptMap`/`StructureMap`. | M |
| CAP-REG-003 | Manage national **extensions** layered over the core ePI model, from an approved registry. | M |
| CAP-REG-004 | Version profiles and mappings with effective dates (to absorb standards flux). | M |
| CAP-REG-005 | Publish profiles/mappings for consumption by #3 (templates), #11 (validation), #12 (completeness), #4 (migration transforms). | M |
| CAP-REG-006 | Add a new market/regulator by configuration (#21) without a code release. | M |
| CAP-REG-007 | Track the conformance target per market (which IG/profile version is authoritative). | M |
| CAP-REG-008 | Validate profile internal consistency before activation. | S |

## 10.4 Content & data model
FHIR conformance resources: `StructureDefinition` (profiles/extensions), `ImplementationGuide` packages, `StructureMap`/`ConceptMap` (mappings), value-set references (#6); per-market configuration (active profile version, extensions) as config-as-data (#21).

## 10.5 Standards & regulatory mapping
HL7 FHIR conformance framework; HL7 Global Core ePI IG; EMA EMRN ePI IG; FDA SPL; national IGs/profiles. This capability is where scheme differences are formally represented.

## 10.6 Lifecycle / owned state
Owns **profile and mapping versions and their state** (draft, active, retired).

## 10.7 Business rules & validation
A market's templates (#3) and checks (#11/#12) must reference an **active** profile version; profile/mapping changes are versioned and audited; extensions must come from the approved registry; retiring a profile version requires a successor for active markets.

## 10.8 Interfaces
- **Exposes:** profile/mapping/extension registry; per-market conformance target.
- **Consumes:** #6 (value sets), #21 (market config), #19 (audit); used by #3, #11, #12, #4, #2.

## 10.9 Acceptance criteria / conformance
- A new market is onboarded via configuration with its conformance profile, consumable by templates and checks.
- Validation and completeness use the correct (active) profile version per market.
- An SPL mapping is available to migration (#4) and to US publishing.
- A national extension is available to the content model (#2) without core changes.

## 10.10 Dependencies
#6, #21, #19; used by #3, #11, #12, #4, #2, #8.

## Cross-capability notes (this group)
- **State authority**: #7 is the single lifecycle authority; #8, #9, #10 all attach state of their own (change records, translation status, profile versions) but read label state from #7.
- **Two change origins**: #8 handles source-content changes (CCDS/signals); #5 (D2.2) raises master-data changes - both converge in #8's impact analysis.
- **Profiles are the backbone**: #10 feeds #3 (templates), #11 (validation), #12 (completeness), #4 (migration). Keep profile version identifiers stable and referenced everywhere.
- **CDS-origin chain**: #8 records section-to-source links that #12 (D2.4) uses to flag sections with no approved origin.
