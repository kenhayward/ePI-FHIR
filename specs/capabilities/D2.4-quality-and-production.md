# Capability 11 - Validation & Quality (VAL)

## 11.1 Purpose & scope
**Technical validation**: FHIR resource conformance against the applicable profile(s) (#10), terminology binding validation (#6), structural well-formedness and reference integrity (#2). Distinct from #12 (regulatory completeness/governance). Runs at defined gates and interactively during authoring.

Out of scope: completeness against market templates and business/compliance rules (#12); lifecycle transitions (#7, which consume validation outcomes).

## 11.2 Actors & flows
Author (interactive feedback), automated pipeline (gates), migration (#4 batch). Flow: content is validated on ingest, on save, pre-approval, and pre-publish against the active profile and bindings, producing structured issues.

## 11.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-VAL-001 | Validate FHIR resource conformance against the applicable active profile(s) from #10. | M |
| CAP-VAL-002 | Validate terminology bindings from #6, honouring binding strength (required/extensible/preferred). | M |
| CAP-VAL-003 | Validate structural well-formedness and reference integrity (#2), including no dangling references in approval candidates. | M |
| CAP-VAL-004 | Run validation at defined gates: ingest (#1), save/author (#3), pre-approval (#7), pre-publish (#14). | M |
| CAP-VAL-005 | Produce structured, actionable issues with severity and precise location (section/element). | M |
| CAP-VAL-006 | Support batch validation for migration (#4). | S |
| CAP-VAL-007 | Configurable rule severity/strictness per gate and per market (#21). | S |
| CAP-VAL-008 | Expose validation via API and as interactive authoring feedback. | M |

## 11.4 Content & data model
Validation result (FHIR `OperationOutcome`-style) with issues (severity, code, location, message); per-gate validation profile set; configuration for severity mapping (#21).

## 11.5 Standards & regulatory mapping
FHIR validation framework and profiles (#10); terminology validation (#6). Aligns with the ePI IG conformance expectations.

## 11.6 Lifecycle / owned state
Does not own label state; owns validation-result records. Gate outcomes are consumed by #7 to permit/block transitions.

## 11.7 Business rules & validation
A version with unresolved error-severity issues cannot pass its gate (per policy); warnings may pass with recorded justification; validation always runs against the profile version active for the content's market/date.

## 11.8 Interfaces
- **Exposes:** validation API; interactive feedback; batch validation.
- **Consumes:** #2 (structure), #6 (terminology), #10 (profiles), #21 (severity config), #19 (audit); used by #1, #3, #4, #7, #14, #12.

## 11.9 Acceptance criteria / conformance
- Nonconformant content is flagged with precise location and severity; conformant content passes.
- Approval/publish gates block on unresolved errors.
- Validation uses the correct active profile and terminology versions.

## 11.10 Dependencies
#2, #6, #10, #21, #19; serves #1, #3, #4, #7, #12, #14.

# Capability 12 - Compliance & Completeness Checking (CMP)

## 12.1 Purpose & scope
**Regulatory completeness and governance**: completeness against the market template (#3), missing mandatory sections, section-level structural issues, configurable business/compliance rules, and **CDS-origin traceability** - flagging label sections with no approved source origin (using #8 lineage). This is the dedicated compliance capability; it consumes the template (#3), profiles (#10), and change lineage (#8).

Out of scope: technical FHIR validity (#11); defining the target structure (#10).

## 12.2 Actors & flows
QA/compliance, reviewer, author. Flow: run completeness and compliance checks against the market template/profile and the CDS-origin lineage -> produce a compliance report -> gate approval/publish.

## 12.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-CMP-001 | Check completeness against the market template (#3) and active profile (#10): required sections present, correctly ordered, and populated. | M |
| CAP-CMP-002 | Detect missing mandatory sections and unexpected/extra sections. | M |
| CAP-CMP-003 | Detect section-level structural/compliance issues beyond FHIR validity. | M |
| CAP-CMP-004 | Run configurable business/compliance rule sets via a rule engine (config-as-data, #21), per market. | M |
| CAP-CMP-005 | Perform the **CDS-origin check**: flag every label section with no approved source origin, using #8's section-to-source lineage. | M |
| CAP-CMP-006 | Produce a compliance report per label/market with rationale and traceability for each finding. | M |
| CAP-CMP-007 | Gate approval/publish on compliance outcome (blocking severities configurable). | M |
| CAP-CMP-008 | Version compliance rule sets with effective dates and audit. | S |

## 12.4 Content & data model
Compliance report (findings: type, severity, section, rationale, source rule); rule definitions (config-as-data, #21); links to template version (#3), profile version (#10), and CDS-origin lineage (#8).

## 12.5 Standards & regulatory mapping
Market templates/profiles (#3/#10); GxP governance expectations (CDS origin, completeness). Rule sets encode per-market regulatory requirements.

## 12.6 Lifecycle / owned state
Owns compliance-check result records; gate outcomes consumed by #7. Does not own label state.

## 12.7 Business rules & validation
A label failing mandatory completeness cannot be approved (per policy); sections with no approved CDS origin are flagged and block per policy; rule sets are versioned and audited; checks use the template/profile version active for the market.

## 12.8 Interfaces
- **Exposes:** compliance/completeness API; compliance reports; gate outcomes.
- **Consumes:** #3 (template yardstick), #10 (profiles), #8 (CDS origin), #6 (terminology), #21 (rules), #19 (audit); used by #7, #14; feeds #23.

## 12.9 Acceptance criteria / conformance
- A label missing a mandatory section is flagged and blocked.
- A section with no approved CDS origin is flagged.
- A compliant label passes with a traceable report.
- Checks run against the correct market template/profile version.

## 12.10 Dependencies
#3, #10, #8, #21, #6, #7, #19, #23.

# Capability 13 - Rendering & Transformation (RND)

## 13.1 Purpose & scope
Renders the **electronic representations** from the FHIR source: **FHIR -> HTML -> PDF**, applying QRD/market styling, branding, and accessibility. This produces the **rendered-PDF lineage**, kept explicitly distinct from the agency **artwork-PDF** (D1 Section 3.3). Also performs scheme transformations where needed (e.g. FHIR ePI -> SPL for US) in coordination with #10 mappings.

Out of scope: authoring artwork (out of scope entirely); publishing/distribution (#14).

## 13.2 Actors & flows
Automated pipeline, author (preview), publisher. Flow: render a label version to HTML and PDF, applying the market render template; produce watermarked draft previews and official renders for approved versions.

## 13.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-RND-001 | Render FHIR ePI to accessible, structured HTML. | M |
| CAP-RND-002 | Render FHIR ePI to PDF for regulatory/electronic distribution (the rendered-PDF lineage, distinct from artwork PDF). | M |
| CAP-RND-003 | Apply market/QRD styling templates and branding via versioned render templates. | M |
| CAP-RND-004 | Produce interactive author previews (draft, watermarked) and official renders (approved). | M |
| CAP-RND-005 | Meet accessibility conformance (WCAG) for HTML output; consider PDF/UA and PDF/A for distribution/archival. | S |
| CAP-RND-006 | Perform scheme transformations where required (e.g. FHIR ePI -> SPL), using #10 mappings. | S |
| CAP-RND-007 | Deterministic, reproducible renders (same input+template version -> same output). | M |
| CAP-RND-008 | Bounded, observable rendering pipeline; asynchronous for heavy renders. | S |
| CAP-RND-009 | Link rendered outputs to the exact label version and render-template version. | M |

## 13.4 Content & data model
Render template/stylesheet (versioned); render job (status, inputs, outputs); output artifacts (HTML, rendered PDF) linked to label version + render-template version; asset store references.

## 13.5 Standards & regulatory mapping
FHIR ePI source (#2); EU QRD styling; WCAG (HTML), PDF/UA and PDF/A candidates for accessibility/archival; SPL as a transformation target (#10).

## 13.6 Lifecycle / owned state
Owns render-job states and output artifacts; outputs tied to a specific label version (state owned by #7).

## 13.7 Business rules & validation
Only approved versions produce official renders; drafts produce watermarked previews; render templates are versioned and the version is recorded on outputs; the rendered-PDF and artwork-PDF lineages are never conflated.

## 13.8 Interfaces
- **Exposes:** render API (preview + official); output artifacts.
- **Consumes:** #2 (content), #10 (mappings/styling profiles), #6 (terminology display), #21 (render config), #19 (audit); serves #14 (publish), #7 (preview).

## 13.9 Acceptance criteria / conformance
- An approved ePI renders to accessible HTML and PDF deterministically.
- Draft previews are watermarked and distinguishable from official renders.
- Rendered PDF is never confused with an agency artwork PDF.
- Outputs record their label and render-template versions.

## 13.10 Dependencies
#2, #10, #6, #21, #19; serves #14, #7.

# Capability 14 - Publishing & Distribution (PUB)

## 14.1 Purpose & scope
Publishes approved ePI and its representations to downstream **channels**: national regulator databases/portals, a company ePI repository/API, and syndication feeds - with **scheduled/effective-dated publication and embargo** handling. It provides the clean published-content API that the **future consumer-delivery system** (option A boundary) will build on. Supports withdrawal/unpublish and republication.

Out of scope: consumer-facing delivery/focusing (out of scope, option A); rendering (#13); submission dispatch (#24).

## 14.2 Actors & flows
Publisher/regulatory ops, channel integrations, downstream consumers. Flow: on approval and effective date (#7), publish FHIR + rendered representations (#13) to configured channels; serve a published API/feed; handle embargo, withdrawal, and republication.

## 14.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-PUB-001 | Publish approved ePI (FHIR) and rendered representations (HTML/PDF from #13) to configured channels. | M |
| CAP-PUB-002 | Support channel types: national regulator databases/portals, company ePI repository/API, and syndication feeds. | M |
| CAP-PUB-003 | Support scheduled/effective-dated publication and embargo, aligned to #7 effective dates. | M |
| CAP-PUB-004 | Provide a clean published-content API/feed for downstream consumers, including the future consumer-delivery system. | M |
| CAP-PUB-005 | Support unpublish/withdrawal and republication, propagating to channels. | M |
| CAP-PUB-006 | Track publication status and history per label version, market, and channel. | M |
| CAP-PUB-007 | Idempotent, retryable channel delivery with receipt confirmation where the channel supports it. | S |
| CAP-PUB-008 | Route publication per market to the correct channel set via configuration (#21). | M |
| CAP-PUB-009 | Emit publication events (#20) and feed reporting (#23). | S |

## 14.4 Content & data model
Publication record (label version, market, channel, status, timestamps, receipts); channel configuration (endpoint, format, credentials via #24/#18); published API/feed model. Channel adapters realised via #24 in D3.

## 14.5 Standards & regulatory mapping
FHIR RESTful API for distribution; national channel formats/protocols (per market); effective-date/embargo semantics; option-A boundary means the published API is the integration point for external consumer systems.

## 14.6 Lifecycle / owned state
Owns **publication states** per channel (scheduled, published, withdrawn, failed). Label lifecycle remains with #7.

## 14.7 Business rules & validation
Only approved and effective versions publish; embargo and effective dates are enforced (no early publication); withdrawal propagates to all channels; per-market routing is configuration-driven; delivery is idempotent and retryable.

## 14.8 Interfaces
- **Exposes:** publication API/feed (the option-A downstream contract); publication status/history.
- **Consumes:** #7 (approved+effective versions), #13 (renders), #24 (channel adapters), #21 (routing config), #18/#17 (secure access), #20 (events); feeds #23.

## 14.9 Acceptance criteria / conformance
- An approved label publishes on its effective date to the correct market channels.
- Embargo prevents early publication; withdrawal removes/supersedes published content.
- The published API serves the current approved content for a product/market/language to authorised consumers.
- Publication status is tracked per channel with retries on transient failure.

## 14.10 Dependencies
#7, #13, #24, #21, #20, #23, #17, #18, #19.
