# Capability 20 - Notifications, Events & Subscriptions (EVT)

## 20.1 Purpose & scope
The **event backbone** the platform rides on: publish/subscribe across capabilities, **FHIR Subscription** for content changes, and notifications that **alert affiliates and consumers** when a change (#8) or new version (#7/#14) affects them. Change propagation, near-real-time impact analysis, and integration all depend on it (D1 Section 6 decision).

Out of scope: the business logic of change (#8) or publication (#14); external transport adapters (#24, which events flow through).

## 20.2 Actors & flows
All capabilities (emit/consume), affiliate users (notifications), external systems (subscriptions/webhooks). Flow: a capability emits an event -> the backbone routes it to internal consumers, user notifications, and external subscribers -> delivery is confirmed/retried.

## 20.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-EVT-001 | Provide a publish/subscribe event backbone for inter-capability communication. | M |
| CAP-EVT-002 | Support FHIR Subscription for content/resource change notifications. | M |
| CAP-EVT-003 | Deliver user notifications (in-app, email) and external webhooks. | M |
| CAP-EVT-004 | Alert affiliates/consumers when a change (#8) or new version (#7/#14) affects their scope. | M |
| CAP-EVT-005 | Provide at-least-once delivery with retries and dead-letter handling; ordering where required. | M |
| CAP-EVT-006 | Maintain an event catalogue/schema registry (config-as-data, #21). | S |
| CAP-EVT-007 | Scope notifications by permission/attribute (#17). | M |
| CAP-EVT-008 | Route all events to the audit sink (#19) where GxP-relevant. | M |

## 20.4 Content & data model
Event schema (type, source, subject, payload, timestamp); subscription (topic/criteria, channel, endpoint); delivery record (status, attempts). Backbone technology chosen in D3 (see mandated-vs-open components).

## 20.5 Standards & regulatory mapping
FHIR Subscription; standard messaging semantics. GxP-relevant events flow to audit (#19).

## 20.6 Lifecycle / owned state
Owns **subscription and delivery states**.

## 20.7 Business rules & validation
At-least-once delivery with idempotent consumers; notifications are permission-scoped; failed deliveries retry then dead-letter (never silently lost); event schemas are versioned.

## 20.8 Interfaces
- **Exposes:** event bus, subscription management, notification delivery.
- **Consumes:** #17 (scoping), #19 (audit), #21 (schema/config), #24 (external transport); emitted/consumed by all capabilities, heavily by #5, #7, #8, #9, #14.

## 20.9 Acceptance criteria / conformance
- An event is delivered reliably to internal and external subscribers, with retry on failure.
- An affiliate is notified when a change affects a label in their scope.
- A FHIR Subscription fires on the relevant content change.
- Notifications respect permission scope.

## 20.10 Dependencies
#17, #19, #21, #24; backbone for all capabilities.

# Capability 21 - Configuration & Business-Rule Management (CFG)

## 21.1 Purpose & scope
Externalised, **config-as-data** management of validation/compliance rules, lifecycle state models, workflows, template and terminology bindings, publishing routing, event schemas, and market/regulator definitions - so a new country, rule, or scheme is a **configuration change, not a code release** (D1 Section 6 decision). Foundational (P0) to extensibility and to controlled, validatable change (GxP/GAMP 5).

Out of scope: the runtime that consumes config (each owning capability); code deployment.

## 21.2 Actors & flows
Administrator, business/regulatory configuration owner. Flow: define/manage configuration and rules -> validate -> govern/approve (with #16/#17) -> promote across environments with effective dates.

## 21.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-CFG-001 | Externalise configuration for markets/regulators, lifecycle state models, workflows, validation/compliance rules, terminology bindings, publishing routing, and event schemas. | M |
| CAP-CFG-002 | Provide a business-rule engine (rules as data) consumed by #11, #12, and lifecycle (#7). | M |
| CAP-CFG-003 | Version configuration and rules with effective dates and full audit (#19). | M |
| CAP-CFG-004 | Onboard a new market/regulator via configuration without a code release. | M |
| CAP-CFG-005 | Govern configuration changes with approval (via #16) and access control (#17). | M |
| CAP-CFG-006 | Validate configuration consistency before activation. | M |
| CAP-CFG-007 | Support environment-aware configuration (dev/test/prod) with controlled promotion (GxP/CSV). | M |

## 21.4 Content & data model
Configuration items and rule definitions (as data); version lineage with effective dates; environment bindings; approval/governance metadata. Rule representation (e.g. decision tables/expression language) decided in D3.

## 21.5 Standards & regulatory mapping
Config-as-data; GAMP 5 configuration management and controlled release; changes are versioned/audited for CSV.

## 21.6 Lifecycle / owned state
Owns **configuration and rule versions and their state** (draft, active, retired) across environments.

## 21.7 Business rules & validation
Configuration changes are versioned, validated, approved, and audited before activation; promotion across environments is controlled; a new market is deliverable via configuration; invalid configuration cannot be activated.

## 21.8 Interfaces
- **Exposes:** configuration/rule management and resolution services.
- **Consumes:** #16 (approval), #17 (access), #19 (audit); serves #5, #6, #7, #9, #10, #11, #12, #14, #16, #20, and others.

## 21.9 Acceptance criteria / conformance
- A new market is onboarded via configuration alone.
- A rule change is versioned, effective-dated, approved, and audited.
- Invalid configuration is blocked before activation; promotion is controlled per environment.

## 21.10 Dependencies
#16, #17, #19; serves nearly all capabilities.

# Capability 22 - Records Retention & Archival (RET)

## 22.1 Purpose & scope
**GxP retention** schedules, archival, **legal hold**, and defensible disposition of labels, versions, renders, and audit records. Ensures regulated records remain available and readable for their required retention period and are disposed of only defensibly.

Out of scope: the audit record's creation (#19, whose records this capability retains); operational storage (D3).

## 22.2 Actors & flows
Records manager, compliance, legal, administrator. Flow: apply retention schedules -> archive long-term -> apply legal hold when required -> defensible disposition at end of retention (approved and audited).

## 22.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-RET-001 | Define and apply retention schedules per record type and market (config-as-data, #21). | M |
| CAP-RET-002 | Archive content, versions, rendered outputs, and audit records for long-term retention. | M |
| CAP-RET-003 | Apply legal hold that overrides scheduled disposition. | M |
| CAP-RET-004 | Perform defensible disposition/destruction at end of retention, with approval (#16) and audit (#19). | M |
| CAP-RET-005 | Ensure archived records remain reconstructable and readable (format longevity). | M |
| CAP-RET-006 | Coordinate audit-record retention with #19. | M |
| CAP-RET-007 | Support immutable/WORM archival where required. | S |

## 22.4 Content & data model
Retention policy (record type, market, period); archival store references; legal-hold records; disposition records (approval, audit link). Coordinated with #19 for audit retention.

## 22.5 Standards & regulatory mapping
GxP record retention; ALCOA+ (enduring, available); legal-hold practice; regional retention requirements per market (config).

## 22.6 Lifecycle / owned state
Owns **retention, hold, and disposition states**.

## 22.7 Business rules & validation
No disposition while under legal hold; disposition requires approval and is audited; records are retained per the applicable schedule; archived records remain readable/reconstructable for the retention period.

## 22.8 Interfaces
- **Exposes:** retention/hold/disposition management; archival access.
- **Consumes:** #21 (schedules), #16 (disposition approval), #17 (access), #19 (audit + audit-record retention); retains records from #7, #13, #14, #19.

## 22.9 Acceptance criteria / conformance
- A record is retained for its scheduled period and remains readable.
- Legal hold blocks disposition; disposition is approved and audited.
- Audit records are retained in coordination with #19.

## 22.10 Dependencies
#19, #21, #16, #17; retains records from #7, #13, #14.

# Capability 23 - Reporting & Analytics (RPT)

## 23.1 Purpose & scope
**Operational and regulatory reporting**: dashboards and metrics across the platform (throughput, backlog, cycle time, publication coverage) and compliance/regulatory reporting (completeness, change propagation, overdue variations, CDS-origin gaps). Management-facing reporting distinct from inspection-grade audit (#19).

Out of scope: the immutable audit record and inspection tooling (#19); operational event transport (#20).

## 23.2 Actors & flows
Management, regulatory ops, QA, administrator. Flow: aggregate data/events across capabilities -> dashboards and scheduled/ad-hoc reports -> distribute, scope-respecting.

## 23.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-RPT-001 | Provide operational dashboards: throughput, backlog, cycle times, publication status/coverage. | M |
| CAP-RPT-002 | Provide regulatory/compliance reports: completeness (#12), change propagation (#8), overdue variations, CDS-origin gaps. | M |
| CAP-RPT-003 | Provide change-impact and propagation reporting sourced from #8. | S |
| CAP-RPT-004 | Provide publication/coverage reporting per market and product (from #14). | S |
| CAP-RPT-005 | Support ad-hoc query/report building and export. | S |
| CAP-RPT-006 | Distribute scheduled reports to authorised recipients. | C |
| CAP-RPT-007 | Respect access scope (#17) in all reporting. | M |

## 23.4 Content & data model
Analytics store/warehouse (read model over capability data/events); report/dashboard definitions; metric definitions with lineage. Physical analytics platform chosen in D3.

## 23.5 Standards & regulatory mapping
BI/analytics; data sourced read-only from all capabilities. Not a substitute for the Part 11 audit trail (#19).

## 23.6 Lifecycle / owned state
None owned; read/analytical layer.

## 23.7 Business rules & validation
Reporting respects permission scope (#17); metrics have defined lineage and are consistent across reports; reporting reads do not alter operational data.

## 23.8 Interfaces
- **Exposes:** dashboards, reports, export.
- **Consumes:** #20 (events) and read APIs from #7, #8, #12, #14, #19; #17 (scoping), #21 (config).

## 23.9 Acceptance criteria / conformance
- Operational dashboards reflect accurate current state.
- A compliance report lists completeness and CDS-origin gaps and overdue variations.
- Reporting is permission-scoped; metrics are consistent and traceable.

## 23.10 Dependencies
#20, #17, #8, #12, #14, #19, #21.

# Capability 24 - External Integration (INT)

## 24.1 Purpose & scope
The **adapter framework and integration patterns** connecting the system to external systems: RIM/regulatory submission, DMS, identity provider, SPOR/IDMP master-data sources, artwork asset hand-off, notification, and outbound national publishing channels. It isolates external coupling behind adapters and supports the option-A boundary (exposing published content to the future consumer system as an integration consumer).

Out of scope: the business logic of the capabilities it connects (e.g. #5, #8, #14); building the external systems.

## 24.2 Actors & flows
Integration engineers, external systems. Flow: inbound (identity, master data, source changes, artwork) and outbound (submission/variation linkage, publication to channels, notifications/webhooks) via resilient, monitored adapters.

## 24.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-INT-001 | Provide an adapter framework for external systems (RIM/submission, DMS, IdP, SPOR/IDMP, artwork hand-off, notification, national channels). | M |
| CAP-INT-002 | Inbound integrations: IdP/federation (#17), SPOR/IDMP master data (#5), source changes/signals (#8), artwork PDFs (#1). | M |
| CAP-INT-003 | Outbound integrations: submission/variation linkage (#8), publication to national/company channels (#14), notifications/webhooks (#20). | M |
| CAP-INT-004 | Support standard integration patterns (synchronous API/FHIR, events, batch/file) with transformation/mediation. | M |
| CAP-INT-005 | Provide resilience (retry, circuit-break, idempotency) and integration monitoring. | M |
| CAP-INT-006 | Manage connection configuration and credentials securely (#18) with routing config (#21). | M |
| CAP-INT-007 | Expose published content to the future consumer-delivery system as an integration consumer (option A). | S |
| CAP-INT-008 | Audit integration exchanges where GxP-relevant (#19). | M |

## 24.4 Content & data model
Connection configuration; adapter definitions; message logs; transformation maps. Credentials via #18; routing via #21.

## 24.5 Standards & regulatory mapping
REST/FHIR, messaging, and file/batch protocols; per-partner formats (e.g. national channel specifications, SPOR APIs, IdP protocols). Aligns to the mandated-vs-open components (Deliverables Definition Section 11).

## 24.6 Lifecycle / owned state
Owns **integration connection and message states**.

## 24.7 Business rules & validation
Credentials are secured (never plaintext, #18); exchanges are idempotent and resilient; external coupling is isolated behind adapters (no direct capability-to-external coupling); GxP-relevant exchanges are audited.

## 24.8 Interfaces
- **Exposes:** adapter/integration services; connection management; integration monitoring.
- **Consumes:** #18 (secure credentials), #21 (routing config), #19 (audit), #20 (event transport); serves #1, #5, #8, #14, #17.

## 24.9 Acceptance criteria / conformance
- Master data syncs from SPOR/MDM; identity federates from the IdP; artwork PDFs are ingested.
- Submission/variation linkage and publication delivery to channels succeed, with retry on failure.
- The published content is consumable by an external consumer system.
- Failed exchanges are retried, monitored, and audited.

## 24.10 Dependencies
#18, #21, #19, #20; serves #1, #5, #8, #14, #17.
