# Capability 1 - Ingestion & Import (ING)

## 1.1 Purpose & scope
The single controlled on-ramp for content entering the system. It accepts (a) conformant **FHIR ePI Bundles** via API and UI, (b) **source documents** (PDF, HTML, Word) for conversion/authoring, and (c) **agency artwork PDFs** as linked assets (not parsed as ePI). It captures provenance, performs structural pre-validation, stages content, and hands off to the Structured Content Model (#2), Validation (#11), and Lifecycle (#7). Bulk/batch intake for migration (#4) reuses this pipeline.

Out of scope: deep conformance/compliance validation (#11, #12), authoring UX (#3), master-data authorship (#5).

## 1.2 Actors & flows
- **Author** imports a Bundle or source document via UI.
- **Integration/automated feed** submits content via API (e.g. from an upstream system).
- **Migration process (#4)** submits bulk batches.
- **Publisher/regulatory ops** may re-import an externally corrected representation.

Primary flow (Bundle import): submit -> identify type and market -> resolve identifiers against master data (#5) -> structural pre-validation -> capture provenance -> stage -> register a draft version (hand to #7) -> emit `content.ingested` (#20).

Secondary flows: source-document import -> extract/normalise -> route to conversion/authoring (#2/#3); artwork PDF -> classify as artwork asset -> link to label version, no ePI parse; batch import -> per-item processing under a batch context (#4).

## 1.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-ING-001 | Accept FHIR ePI Bundles in JSON and XML via authenticated API and UI upload. | M |
| CAP-ING-002 | Accept source documents (PDF, HTML, Word/DOCX) for downstream conversion/authoring. | M |
| CAP-ING-003 | Accept and classify agency **artwork PDFs**, storing them as managed assets linked to a label version; never parse them as ePI content. | M |
| CAP-ING-004 | Perform structural pre-validation on ingest (well-formed, parseable, required anchors present) before acceptance; delegate deep validation to #11. | M |
| CAP-ING-005 | Capture provenance for every ingested item: source, submitter/actor, timestamp, channel, original filename, and content hash. | M |
| CAP-ING-006 | Retain the original submitted artifact (binary) immutably, linked to the created/staged record. | M |
| CAP-ING-007 | Resolve product/label identity on ingest against master data (#5); flag unresolved identifiers. | M |
| CAP-ING-008 | Quarantine items failing pre-validation into a rejection/exception state with actionable, itemised errors. | M |
| CAP-ING-009 | Detect duplicates by business identifier + version + content hash; apply configurable dedupe policy. | S |
| CAP-ING-010 | Support batch/bulk submission with a batch context, per-item status, and resumability (used by #4). | M |
| CAP-ING-011 | Expose an idempotent ingestion API (safe re-submission without duplicate side effects). | S |
| CAP-ING-012 | Emit ingestion lifecycle events (received, staged, rejected) to the event backbone (#20). | M |
| CAP-ING-013 | Enforce ingestion authorisation and affiliate/market scoping via #17; record to audit (#19). | M |
| CAP-ING-014 | Support configurable per-channel/source ingestion profiles (accepted types, validation strictness) via #21. | S |

## 1.4 Content & data model
- **Ingestion item**: submission metadata, channel, actor, timestamps, content hash, batch reference, status.
- **Provenance**: FHIR `Provenance` referencing the created resource and the original source `Binary`/`DocumentReference`.
- **Original artifact**: `Binary`/`DocumentReference` retained immutably; artwork PDFs carry an asset classification distinguishing them from rendered PDFs (see D1 Section 3.3, two PDF lineages).
- **Staging area**: transient store holding pre-draft content prior to hand-off to #7.

## 1.5 Standards & regulatory mapping
FHIR `Bundle` (type = document) for ePI; `Provenance`, `DocumentReference`, `Binary` for source/artwork; SPL (HL7 v3 XML) accepted as a source type for conversion (transform owned by #4/#13-adjacent mapping). Section/anchor expectations follow the ePI IG (#2).

## 1.6 Lifecycle / owned state
Owns **transient ingestion states** only: `received -> parsing -> staged` or `-> rejected`. On `staged`, control passes to Lifecycle (#7), which owns the label lifecycle from `draft` onward. Ingestion states are auditable but not the label system-of-record state.

## 1.7 Business rules & validation
Reject unsupported media types; quarantine (not drop) on structural failure; enforce dedupe policy; require resolvable identity (or explicit override with reason, audited); artwork PDFs must be linked to an existing label version or held as unlinked assets pending linkage. No silent loss - every submitted item ends in a terminal, queryable state.

## 1.8 Interfaces
- **Exposes:** Ingestion API (single + batch), UI upload, `content.ingested`/`content.rejected` events.
- **Consumes:** Master Data (#5) for identity resolution; Terminology (#6) for lightweight pre-checks; Validation (#11) for deep validation; Lifecycle (#7) for draft registration; IAM (#17), Audit (#19), Config (#21), Events (#20).

## 1.9 Acceptance criteria / conformance
- A valid ePI Bundle is ingested, provenance recorded, original retained, and a draft created in #7.
- A malformed Bundle is rejected with itemised, actionable errors and no partial state.
- An artwork PDF is stored and linked as an asset and is never surfaced as ePI content.
- A batch of N items yields N terminal per-item statuses with a reconciling batch summary; a mid-batch failure is resumable.

## 1.10 Dependencies
#2 (content model), #5 (identity), #6 (terminology pre-check), #7 (lifecycle), #11 (validation), #17 (access), #19 (audit), #20 (events), #21 (config); consumed by #4 (migration).

# Capability 2 - Structured Content Model (SCM)

## 2.1 Purpose & scope
Defines the **canonical FHIR ePI information model** that the entire system reads and writes: the document `Bundle` anchored by a `Composition` with typed sections, the referenced product-data resource graph, the extension mechanism, content reuse/single-sourcing, and cross-references. This is the foundational model (P0); it is the single source of truth from which all representations derive.

Out of scope: physical storage (D3); template scaffolding (#3); conformance profile definition per market (#10, consumed here); completeness rules (#12).

## 2.2 Actors & flows
Primarily a foundational service consumed by other capabilities rather than used directly by end users. Authors interact via #3/authoring; rendering (#13) and validation (#11) read the model. Flows: represent an ePI as structured content; compose/replace sections; reference product data; define and resolve reusable content units and cross-references.

## 2.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-SCM-001 | Represent an ePI as a FHIR document `Bundle` anchored by a `Composition` with typed, coded sections. | M |
| CAP-SCM-002 | Support the ePI product-data resource graph by reference (e.g. `MedicinalProductDefinition`, `PackagedProductDefinition`, `ManufacturedItemDefinition`, `AdministrableProductDefinition`, `Ingredient`, `SubstanceDefinition`, `ClinicalUseDefinition`, `RegulatedAuthorization`, `Organization`). | M |
| CAP-SCM-003 | Support both structured (coded, referenceable) and narrative section content. | M |
| CAP-SCM-004 | Provide a **content-reuse / single-sourcing** mechanism: referenceable shared content units (e.g. class labelling, reusable blocks) so one source updates every referencing label. | M |
| CAP-SCM-005 | Support **cross-references** within a document and across documents, with referential integrity and resolution. | M |
| CAP-SCM-006 | Provide a governed **extension** mechanism for market/regulator-specific data without forking the core model. | M |
| CAP-SCM-007 | Define **canonical identifier and versioning semantics** for documents, sections, and reusable units (stable IDs across languages/markets/versions). | M |
| CAP-SCM-008 | Bind section types and coded elements to terminology/value sets from #6. | M |
| CAP-SCM-009 | Expose the content model/schema (profiles, section taxonomy, extensions) as a service to authoring (#3), validation (#11), and rendering (#13). | M |
| CAP-SCM-010 | Preserve full fidelity round-trip: a conformant ePI can be represented and re-serialised without content loss. | M |
| CAP-SCM-011 | Support association of a label document to its product/packaging identity (the product <-> packaging <-> label association model, with #5). | M |
| CAP-SCM-012 | Distinguish canonical content from generated representations (HTML/PDF) and from linked artwork assets. | M |

## 2.4 Content & data model
- **Document**: `Bundle` (document) + `Composition` (metadata, subject = product, sections).
- **Sections**: coded by the ePI/QRD section taxonomy (LOINC/EDQM/EU section codes), ordered, nestable, each structured or narrative.
- **Product graph**: referenced IDMP-aligned resources (see CAP-SCM-002).
- **Reusable content unit**: a referenceable resource (e.g. a governed `Composition`/section fragment or `List`-referenced block) with its own identity and version, embedded by reference into labels.
- **Cross-reference**: typed link resource/extension resolving to a section or unit.
- **Extension registry**: catalogue of approved extensions with definitions (config-as-data with #21/#10).

## 2.5 Standards & regulatory mapping
HL7 Global Core ePI FHIR IG (Bundle/Composition/List and product resources); EMA EMRN ePI profiles; EU QRD section taxonomy; SPL section model mapped at the section-code level (full SPL<->FHIR mapping owned by #10/#4). Terminology bindings via #6.

## 2.6 Lifecycle / owned state
Owns the **structural/version semantics** of content (identity, version lineage of documents/sections/units) but not the editorial/regulatory lifecycle state, which is #7. Reusable-unit version lineage is owned here and consumed by change-impact (#8).

## 2.7 Business rules & validation
Structural constraints (a Composition conforms to its profile's section structure; presence-vs-completeness split: structure here, mandatory-completeness in #12); referential integrity for cross-references and product references (no dangling references in an approved document); a reusable unit change creates a new unit version - referencing labels resolve to a pinned or floating version per policy; extensions must be from the approved registry.

## 2.8 Interfaces
- **Exposes:** content-model/schema service; content read/write model APIs used by #1, #3, #11, #13; reusable-unit resolution.
- **Consumes:** #5 (product identity), #6 (terminology), #10 (conformance profiles), #21 (extension/config).

## 2.9 Acceptance criteria / conformance
- A conformant ePI round-trips with no content loss (CAP-SCM-010).
- A reusable unit referenced by two labels, when updated, is reflected consistently per the resolution policy.
- Cross-references resolve; an approved document contains no dangling references.
- A market-specific datum is carried via an approved extension without altering the core profile.

## 2.10 Dependencies
#5, #6, #10, #21; foundational to and consumed by #1, #3, #7, #8, #11, #12, #13, #14.

# Capability 3 - Template & Label-Type Management (TPL)

## 3.1 Purpose & scope
A managed, versioned library of **label-type templates** that turn per-market conformance profiles (#10) into **authorable skeletons**: pre-scaffolded ePI structures with mandatory sections, section metadata, terminology bindings, and default/boilerplate content, so authors work template-driven rather than hand-building raw FHIR. Supports deriving market/language variant templates from a core template, template versioning, and template lifecycle.

Out of scope: the label's own content lifecycle (#7); completeness checking of an authored label (#12, which uses the template as the yardstick).

## 3.2 Actors & flows
- **Template owner** creates/updates/retires templates and maps them to conformance profiles.
- **Author** instantiates a new label from a template and authors within it.
- **Administrator** manages template access and library structure.

Flows: create template (define sections, mandatory flags, order, metadata, terminology bindings, defaults, target profile) -> approve (via #16) -> publish to library; instantiate label from approved template -> conformant scaffold draft (to #7); derive variant template (inherit core + override within allowed bounds); evolve template version (new version, effective date, impact list of labels created from prior versions).

## 3.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-TPL-001 | Maintain a versioned library of templates keyed by label type, market/regulator, and product type. | M |
| CAP-TPL-002 | A template defines section structure, mandatory/optional flags, ordering, section metadata, terminology bindings, and default/boilerplate content. | M |
| CAP-TPL-003 | Each template targets a conformance profile from #10 (the structure it must produce). | M |
| CAP-TPL-004 | Instantiate a new label from a template, producing a conformant, pre-scaffolded draft handed to #7. | M |
| CAP-TPL-005 | Provide template-driven **guided authoring**: field-level guidance, allowed value sets (#6), and section prompts that shield authors from raw FHIR. | M |
| CAP-TPL-006 | Derive **variant templates** from a core template via inheritance with controlled add/override (market/language variants). | M |
| CAP-TPL-007 | Version templates with effective dates; record which template (and version) each label was instantiated from. | M |
| CAP-TPL-008 | Support template lifecycle (draft, in-review, approved, retired) with approval via #16 and access via #17 (template-owner role). | M |
| CAP-TPL-009 | On template change, list impacted labels (those created from prior versions) for optional re-alignment; never mutate existing labels automatically. | M |
| CAP-TPL-010 | Validate a template's own structural correctness against its target profile before it can be approved. | S |
| CAP-TPL-011 | Support boilerplate/default content as reusable units (#2) so shared text is single-sourced across templates. | S |
| CAP-TPL-012 | Allow configurable policy on instantiation from non-approved templates (block by default). | S |

## 3.4 Content & data model
- **Template**: structured definition (section tree with flags/metadata/bindings/defaults) + reference to target conformance profile (#10). Candidate FHIR representations: `Questionnaire` (authoring form) plus `StructureDefinition`/profile linkage, and/or a template `Composition` skeleton; final representation decided in D3.
- **Template version**: versioned artifact with effective dates and lineage.
- **Instantiation record**: links a label to its source template + version (pinned).
- **Variant/inheritance**: parent-child template relationship with override set.

## 3.5 Standards & regulatory mapping
EU QRD templates; EU SmPC/PL structures; SPL section model; national variants - each expressed as a template targeting the corresponding conformance profile (#10). Terminology bindings via #6.

## 3.6 Lifecycle / owned state
Owns **template lifecycle state** (draft, in-review, approved, retired) and template version lineage - distinct from label lifecycle (#7).

## 3.7 Business rules & validation
Cannot instantiate from a non-approved template (unless config permits); a variant may only add/override within bounds the core allows; a template change produces a new version and does not alter existing labels (they pin their template version); a template must validate against its target profile before approval; retiring a template blocks new instantiation but preserves existing labels and history.

## 3.8 Interfaces
- **Exposes:** template CRUD, approve, instantiate, derive-variant APIs; impacted-label list; guided-authoring definition to the authoring UI.
- **Consumes:** #2 (content model, reusable units), #6 (terminology/value sets), #10 (conformance profiles), #16 (approval workflow), #17 (access/roles), #11 (template self-validation), #21 (config).

## 3.9 Acceptance criteria / conformance
- A label instantiated from an approved template passes structural validation (#11) and template-completeness for the target market (#12).
- The created label records its template version (pinned); a later template change does not mutate it but appears on the impacted-label list.
- A derived market variant preserves the core structure plus its declared overrides.
- Guided authoring only offers value-set-valid options for bound fields.

## 3.10 Dependencies
#2, #6, #10, #11, #12, #16, #17, #21; enables authoring for #1 (instantiated drafts) and is the yardstick source for #12.

# Capability 4 - Data Migration & Legacy Onboarding (MIG)

## 4.1 Purpose & scope
One-time and ongoing **bulk onboarding of legacy labels** (PDF, SPL XML, Word/HTML) into the structured content model: classify, convert/extract, map to template/profile, validate, reconcile against source, and load. It shapes the ingestion/conversion architecture and is therefore specified in target planning even though it runs at scale in a later phase (P4); its tooling is built earlier.

Out of scope: the ongoing single-item ingestion path (#1, reused here); authoring UX (#3); publishing of migrated content (#14).

## 4.2 Actors & flows
- **Migration engineer/operator** configures and runs batches.
- **QA reviewer** works the reconciliation/remediation queue.
- **Author** remediates low-confidence conversions.

Flow: intake legacy set (via #1 batch) -> classify by format/type/market -> convert/extract to structured draft (#2), template-aligned (#3) -> transform SPL->FHIR where applicable -> validate (#11) -> reconcile converted vs source (confidence, gaps) -> route low-confidence/failed to remediation -> load at a configured lifecycle state (#7) with provenance to the legacy source.

## 4.3 Functional requirements

| ID | Requirement | Pri |
|---|---|---|
| CAP-MIG-001 | Provide a bulk import pipeline for legacy formats (PDF, SPL XML, Word/HTML) at scale, built on the #1 batch path. | M |
| CAP-MIG-002 | Automated extraction/conversion of legacy content into the structured model (#2), aligned to a target template/profile (#3/#10). | M |
| CAP-MIG-003 | Transform SPL (HL7 v3) sources into FHIR ePI via a maintained mapping. | M |
| CAP-MIG-004 | Produce a **reconciliation report** per item and per batch: converted vs source coverage, confidence score, and identified gaps. | M |
| CAP-MIG-005 | Route low-confidence or failed items to a **remediation workflow** (human-in-the-loop); never silently drop items. | M |
| CAP-MIG-006 | Configurable target lifecycle state for migrated items (e.g. imported-historical vs active-approved), defaulting to non-approved. | M |
| CAP-MIG-007 | Capture provenance linking each migrated label to its legacy source artifact (retained immutably). | M |
| CAP-MIG-008 | Batch runs are idempotent, resumable, and fully auditable; dropped/failed/deduped items are logged, not hidden. | M |
| CAP-MIG-009 | Deduplicate against already-loaded content by identifier/version/hash. | S |
| CAP-MIG-010 | Provide throughput/scale controls (throttling, parallelism) and progress reporting for large backfills. | S |
| CAP-MIG-011 | Support dry-run/simulation mode producing reconciliation output without loading. | S |
| CAP-MIG-012 | Emit migration job and item events (#20) for monitoring and reporting (#23). | S |

## 4.4 Content & data model
- **Migration job**: config (source set, target template/profile, target state, dedupe policy), status, metrics.
- **Migration item**: per-source-artifact record with status, confidence, gaps, links to created draft and source `Binary`/`DocumentReference`.
- **Provenance**: FHIR `Provenance` from migrated label to legacy source.
- **Mapping config**: SPL->FHIR and format->section mappings (config-as-data, #21).

## 4.5 Standards & regulatory mapping
Source: SPL (HL7 v3 XML), plus unstructured PDF/Word/HTML. Target: FHIR ePI (#2) aligned to QRD/market templates (#3/#10). Mapping fidelity and section-code alignment are explicit and versioned.

## 4.6 Lifecycle / owned state
Owns **migration job and item states** (queued, running, partial, complete, failed; per-item: converted, low-confidence, failed, remediated, loaded). Loaded items enter the label lifecycle (#7) at the configured state.

## 4.7 Business rules & validation
Never auto-approve unless explicitly configured; low-confidence/failed items must be remediated or explicitly rejected (with reason, audited); retain every source artifact; dedupe before load; a batch reports a full reconciliation (submitted = loaded + remediation-queued + rejected + deduped), enforcing no-silent-truncation.

## 4.8 Interfaces
- **Exposes:** migration job API (create, run, dry-run, resume), reconciliation reports, remediation queue.
- **Consumes:** #1 (batch ingestion), #2 (content model), #3 (templates), #10 (profiles/mapping), #11 (validation), #7 (lifecycle load), #19 (audit), #20 (events), #21 (mapping config); feeds #23 (reporting).

## 4.9 Acceptance criteria / conformance
- A legacy SPL/PDF set loads with a per-item and per-batch reconciliation report.
- Low-confidence items appear in the remediation queue; none are dropped silently.
- Each migrated label has provenance to its retained legacy source.
- Re-running a completed batch is idempotent (no duplicates); a dry run produces reconciliation output with zero loads.

## 4.10 Dependencies
#1, #2, #3, #10, #11, #7, #19, #20, #21; feeds #23.
